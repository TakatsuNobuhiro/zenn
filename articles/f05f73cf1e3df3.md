WordPressで運営していたフットサル戦術ブログ「futsal.tech」を、Next.js 16のApp Routerへ移行しました。

昨今騒ぎになっているPHPの脆弱性などもあり、WordPressの保守をやめたいという理由と、最近はAIで校正しながら記事を執筆するようになったので、Git連携してソースコードと一緒に記事を管理し、SSGしたいという理由で移行しました。結論、AIを駆使してほぼ１日で移行を完了することができ、本当にやってよかったなと思っています。

この記事では、その移行手順などを備忘録として残したいと思います。

## なぜ移行したのか

簡単に言うと、WordPressがAIフレンドリーではないことと、保守コストがどんどん増えていたことが理由です。

WordPressだと基本的に管理画面のGUIで記事を編集することになります。Next.jsへ移行すれば、記事をローカルでMarkdownとして管理できるようになります。Markdownで書いた原稿をAIに校正してもらったり、多言語に翻訳してもらったりと、執筆まわりの作業をAIで自動化しやすくなるのが大きいです。

もちろん、AIだけで書いた質の低い記事を量産したいわけではありません。ただ、ブログをグロースさせていくうえで、AIを使いにくい環境そのものが生産性のボトルネックになっていると感じていました。

## 移行前の状況

移行元はWordPressのJINテーマで運営していたフットサル戦術ブログです。記事には次のような要素が含まれていました。

- カテゴリを含む階層型パーマリンク
- WordPressのメディアライブラリに保存した画像
- Gutenbergのブロックコメント
- JINテーマ固有のHTMLや装飾クラス
- URLを単独で貼ったYouTube・Xの埋め込み
- JINのブログカード
- 目次プラグインのショートコード
- codocによる有料記事
- RSS、サイトマップ、構造化データ

記事本文を手でコピーするだけなら、作業自体はそこまで難しくないです。ただ70記事ぶんやると確実に表記が揺れますし、リンクの張り替え漏れも出てきます。しかも間違いに気づいたときにやり直しがききません。なので、WordPress標準のWXRエクスポートを入力にして、Markdownへ一括変換する方針にしました。

## 最初に決めたこと：WordPressを再現しすぎない

移行先では、WordPressの内部構造をそのままNext.jsへ持ち込まないようにしました。

WordPressでは投稿、固定ページ、カテゴリ、添付ファイルなどがデータベースに保存されていて、テーマとプラグインが表示を組み立てています。移行後は、記事をMarkdown、メタデータをfrontmatter、画像を静的ファイルとしてGitで管理する構成にしました。

```text
content/
  posts/**/*.md
  pages/*.md
  categories.json

public/
  images/posts/**

scripts/migrate/
  parse-wxr.ts
  build-category-map.ts
  html-to-markdown.ts
  wxr-to-markdown.ts
```

それぞれの役割は以下の通りです。

- `parse-wxr.ts`でWXRを解析する
- `build-category-map.ts`で親子カテゴリを復元する
- `html-to-markdown.ts`でWordPress由来のHTMLをMarkdownへ変換する
- `wxr-to-markdown.ts`で記事・固定ページ・画像を所定の場所へ出力する

こうして分けておくと、変換結果がおかしいときに「パーサが悪いのか、HTML変換が悪いのか、出力先が悪いのか」を切り分けやすくなります。移行処理は本番のリクエスト時には動かさず、必要なときだけ叩くバッチとして扱っています。

## WXRをMarkdownへ変換する

### 1. まずWXRを正常に読める状態にする

エクスポートしたWXRをパーサに食わせたところ、いきなり落ちました。XMLとして不正な制御文字が混ざっていたのが原因です。仕方ないので、先に制御文字を取り除いたファイルを作ってから変換するようにしました。

```bash
node -e "require('fs').writeFileSync(
  'wp-mirror/export_clean.xml',
  require('fs')
    .readFileSync('wp-mirror/export.xml', 'utf-8')
    .replace(/[\x00-\x08\x0b\x0c\x0e-\x1f\x7f]/g, '')
)"
```

ここで元ファイルを直接上書きしなかったのが、あとから効いてきました。変換に失敗しても、いつでもエクスポート直後の状態に戻れます。

### 2. URLをfrontmatterとして保持する

各記事は、本文と次のようなfrontmatterへ変換しました。

```yaml
---
title: "記事タイトル"
slug: fixo
wpId: 7457
category: base
categoryPath:
  - base
date: "2025-03-29"
updated: "2025-03-29"
draft: false
excerpt: "記事の要約"
cover: /images/posts/2025/03/cover.jpg
tags: []
---
```

残しておいてよかったなと思ったのが`wpId`と`categoryPath`の2つです。

`wpId`は公開画面では一切使いません。ただ、移行後に「この記事ちゃんと移ってる？」とWordPress側と突き合わせるとき、これがないと照合がかなりつらいです。`categoryPath`のほうは、カテゴリ名を1つだけ持つのではなく、親から子までのパスを配列で持たせました。おかげで`/set-play/opposition-half-ki/chon-don/`のような階層型URLを機械的に再現できました。

今はこれに加えて、`articleId`という不変IDも持たせています。URLやファイル名を変えても購入情報との紐付けが切れないようにするためです。移行した時点では必要性に気づいていなかったのですが、コンテンツを外部システムとつなぐつもりがあるなら、URLともWordPress IDとも別の永続IDを最初から振っておいたほうがいいと思います。

### 3. HTMLを一度正規化してからMarkdown化する

WXRの中身は、想像していたほどきれいなHTMLではありませんでした。Gutenbergのコメント、テーマ固有のラッパー、空段落、目次ショートコードが同じ本文に同居しています。

そのままTurndownに渡すと悲惨なMarkdownが出てくるので、間にCheerioを挟んでDOMとして整理してから渡すようにしました。

やった変換はだいたい以下のあたりです。

- WordPressのブロックコメントを削除
- `[toc]`など目次プラグインの記法を削除
- 空段落を削除
- JINの2カラム用ラッパーを外し、中身だけ残す
- WordPress内の絶対URLをサイト内相対URLへ変換
- `figure`と`figcaption`をMarkdown画像とキャプションへ変換
- `srcset`や`loading`など、移行後に不要な画像属性を除去

ここで悩んだのは、見た目の再現をどこで諦めるかでした。たとえば2カラムのレイアウトは消えてしまいます。それでも、左右に入っていた文章と画像さえ残っていれば記事としては成立します。JIN固有のDOMを新しいサイトに引きずり込むくらいなら、多少見た目が変わってもMarkdownとして読める形にしたいと考えました。

## 画像はURLだけでなくファイル本体も移す

WXRだけでは、画像ファイル本体は移行できません。そのため、WordPressの`wp-content/uploads`を別途取得して、`public/images/posts/{year}/{month}/`へコピーしました。

変換スクリプトでは添付ファイルURLの対応表を作って、本文中の次のようなURLをローカルパスへ置換しています。

```text
https://futsal.tech/wp-content/uploads/2021/08/example.jpeg
↓
/images/posts/2021/08/example.jpeg
```

地味に面倒だったのが、`-300x200`のようなサムネイル用のサイズ接尾辞とクエリ文字列です。本文が縮小版のURLを指していることがあるので、そこも正規化して元画像に寄せるようにしました。

画像のWebP化とレスポンシブ画像の生成は、移行が一段落してから手をつけました。移行と同時にやろうとすると、画像が表示されない原因が「移せていない」のか「変換に失敗した」のか分からなくなってしまいます。まずは欠損ゼロで移すことだけに集中して、配信サイズは後回しにしました。

## URLを変えないことを最優先にした

既存サイトには検索流入があるので、URLが変わるとその影響は大きいです。移行スクリプトでは、WordPressのURLと、`categoryPath`と`slug`から生成したURLを比較して、不一致を一覧化するようにしました。

```ts
const expectedUrl = `${SITE_URL}/${categoryPath.join("/")}/${post.slug}/`;
const normalizedLink = post.link.replace(/\/$/, "") + "/";
const normalizedExpected = expectedUrl.replace(/\/$/, "") + "/";

if (normalizedLink !== normalizedExpected) {
  urlMismatches.push(
    `slug=${post.slug} | WP link: ${post.link} | Generated: ${expectedUrl}`,
  );
}
```

URLを維持できないページには、Next.jsの`redirects()`で301リダイレクトを設定しました。対象は、たとえば次のようなURLです。

- `/feed/`から`/feed.xml`への移行
- `/wp-sitemap.xml`から`/sitemap.xml`への移行
- 旧固定ページを記事として再分類した際のURL変更
- 過去に手作業で作成した別名URL

最初は主要なページだけブラウザで確認するつもりでしたが、70記事を目視で確認すると必ず見落とします。結局、変換のたびに全件比較させるのがいちばん早かったです。検証をスクリプトに組み込んでおけば、変換ロジックを変えるたびに同じ基準でチェックが走るので安心です。

## Next.jsでは1つの動的ルートから静的生成する

移行先はNext.js 16のApp RouterとReact 19で構築しました。記事、カテゴリ、固定ページはcatch-allルートで解決して、`generateStaticParams`と`dynamic = "force-static"`を使って静的生成しています。

```ts
export const dynamic = "force-static";

export async function generateStaticParams() {
  return getAllStaticPaths();
}
```

Markdownは`gray-matter`でfrontmatterと本文に分けて、remark・rehypeのパイプラインでHTMLへ変換しています。記事ページだけでなく、カテゴリ一覧、パンくず、目次、RSS、サイトマップ、JSON-LDも同じコンテンツモデルから生成する構成にしました。

この構成にすると、ページ生成時にWordPressにも外部DBにも問い合わせる必要がありません。記事の更新はMarkdownを直してビルドするだけで済みますし、何をどう直したかはGitの差分に残ります。

## WordPressの「便利だった挙動」を選んで戻す

Markdownに移した直後は、WordPressが勝手にやってくれていた表示がごっそり消えてしまいます。埋め込みのURLがただのリンクになっているのを見て、YouTube・Xの埋め込みと内部リンクカードを慌てて実装しました。

ルールは、自分が覚えていられる範囲に絞っています。

- YouTubeのURLを単独行に置くとレスポンシブな動画へ変換する
- Xの投稿URLを単独行に置くと埋め込みへ変換する
- サイト内URLを単独行に置くとタイトル、抜粋、画像を含むカードへ変換する

HTMLを本文に埋め込まず、Markdown上はURLだけ置いておいて表示時に変換する形です。こうしておくとMarkdownを直接読んでも意味が取れますし、書くときの手間もWordPressの頃とそこまで変わりません。

目次も同じ考え方で、ショートコードは本文に残さず見出しから自動生成しています。表示はスマホではアコーディオン、PCでは追従表示に分けました。プラグインを置き換えるときは、そのプラグインの機能を全部並べるよりも「読者と自分が実際に使っていた部分はどこか」を洗い出すほうが早かったです。

## 移行後に追加した運用の仕組み

初期移行のあとは、次のような順番で機能を追加していきました。

1. WXR変換、Markdown管理、静的ページ生成、YouTube・X埋め込み、内部リンクカード、CI
2. codocのメタデータとペイウォール位置の移行
3. 画像サイズの取得、記事表示コンポーネント、SEOの改善
4. 画像のWebP化、YouTubeリンク切れチェック
5. Xリンク切れチェック、Search Console向けメタデータ
6. 多言語化と翻訳記事の追加
7. レスポンシブWebP画像
8. Cloudflare WorkersとOpenNextによる配信へ移行
9. 課金基盤や検索など、サイト運営機能を拡張

当初のREADMEにはVercelへデプロイすると書いていたのですが、今はCloudflare WorkersとOpenNextに載せ替えています。コンテンツをMarkdownと静的アセットに切り出しておいたおかげで、ホスティングを変えても記事データには一切触らずに済みました。

あとから効いてきたのが、リンク切れチェックをCIに入れたことです。移行した時点で正しく表示できていても、埋め込み先のYouTube動画やXの投稿は勝手に消えてしまいます。移行が終わった時点がゴールではないんだなと実感しました。

## 苦労した点と、やり直すなら変えること

### コンテンツの分類は「投稿か固定ページか」だけでは決まらない

WordPress上は固定ページ扱いなのに、中身は完全に長文の戦術記事というページがいくつかありました。これらは`content/posts/base/`に振り分けて、旧URLから301でリダイレクトしています。

最初はWordPressの投稿タイプをそのまま持ってこようとしていたのですが、途中で「一覧に出すのか、検索に引っかけるのか、関連記事として出すのか」で決めるべきだったと気づきました。

### テーマ固有表現は例外が増えやすい

JINの装飾、Gutenbergコメント、ショートコード、ブログカード、有料記事ブロック。これらは全部それぞれ別の変換ルールが必要で、一つ対応するたびに新しい例外が出てきました。正規表現だけで押し切ろうとすると高確率で壊れるので、DOMとして解析できるものはCheerioに任せて、正規表現は最後の整形だけに限定しました。

先に記事内で使われているブロックとショートコードの種類を集計しておけば、この手戻りはかなり減らせたはずです。

### 不変IDは最初に設計する

移行した時点では、WordPress IDとURLがあれば十分だと思っていました。実際に困ったのは有料記事の購入情報を扱い始めてからで、slugやファイルパスを変えると紐付けが切れてしまうことに気づきました。結局、あとからUUIDベースの`articleId`を追加しています。

分析や課金、翻訳まで手を広げるつもりがあるなら、CMS由来のIDとは別に自前の不変IDを最初に振っておいたほうがいいです。

### 変換結果の品質チェックもコードにする

ビルドが通ることと、記事がちゃんと移っていることは別物でした。今はMarkdown記法、YouTubeリンク、Xリンク、ペイウォール位置を検査するスクリプトを置いていますが、これも全部あとから追加したものです。

最低限これくらいは移行前に自動化しておけばよかったなと思っています。

- WordPressと移行後の公開記事数が一致するか
- URLの一致、または301リダイレクトがあるか
- 参照画像がすべて存在するか
- 内部リンクの遷移先が存在するか
- title、description、canonical、構造化データが出力されるか
- 有料記事の公開範囲が移行前と一致するか

## 実際に使った移行手順

最終的に落ち着いた流れは以下の通りです。

1. WordPress管理画面から全コンテンツをWXRでエクスポートする
2. `wp-content/uploads`を取得する
3. WXRから不正な制御文字を除去する
4. 変換スクリプトを`--dry-run`で実行し、件数とURL差分を確認する
5. Markdown、カテゴリJSON、画像を出力する
6. Next.jsをビルドし、全ページが静的生成されることを確認する
7. 旧URL、RSS、サイトマップ、内部リンク、画像を確認する
8. 変更できないURLは維持し、変更が必要なURLには301リダイレクトを設定する
9. 本番切り替え後も、Search Consoleとリンクチェックで継続監視する

変換コマンドにはdry-runを用意しておきました。

```bash
npx tsx scripts/migrate/wxr-to-markdown.ts --dry-run
npx tsx scripts/migrate/wxr-to-markdown.ts
npm run build
```

同じ入力から何度でも作り直せる。これが手作業でやる場合との一番大きな違いでした。

## まとめ

やってみた感想としては、この移行は単にCMSをフレームワークに置き換える作業ではありませんでした。WordPressが一括で面倒を見てくれていた領域を、コンテンツ、ルーティング、表示、SEO、画像、収益化、運用監視に切り分けて、それぞれ自分で決め直していく作業だったなと思います。

特に効いたと思うのは次の4つです。

1. WXRからMarkdownへの変換をスクリプト化し、再実行可能にする
2. `categoryPath`から旧URLを再現し、全件を機械的に比較する
3. テーマ固有HTMLは見た目ではなく意味を残す形へ正規化する
4. 移行後の改善を前提に、コンテンツと配信基盤を分離する

最初のコミットで記事と画像をまとめて移して、そのあとのコミットで埋め込み、SEO、画像最適化、多言語化、課金、配信基盤を順番に足していきました。70記事を抱えたまま作業を進められたのは、この順番で進めたからだと思います。

これから同じように移行する方には、完成形を一度で作ろうとしないことをおすすめしたいです。まずはURLとコンテンツを落とさずに移す。テーマやプラグインが提供していた機能は、そのあとで一つずつ選び直していけば大丈夫です。
