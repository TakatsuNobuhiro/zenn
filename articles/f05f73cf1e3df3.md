WordPressで運営していたフットサル戦術ブログ「futsal.tech」を、Next.js 16のApp Routerへ移行した。

対象は70記事と3つの固定ページ。本文だけでなく、画像、カテゴリ階層、目次、YouTube・Xの埋め込み、内部リンクカード、有料記事、RSS、サイトマップまでWordPress側に依存していた。しかも、検索流入を落とさないためには既存URLをできる限り変えられない。

この移行で難しかったのは、Reactで画面を作ることではなかった。WordPressが暗黙に担っていた「コンテンツ管理」「URL設計」「テーマ固有の表示」を分解し、Next.js側で再設計することだった。

この記事では、リポジトリのコミット履歴を振り返りながら、実際に採用した構成、移行スクリプトの設計、移行後に発生した問題、そして結果的に何を先に決めるべきだったかをまとめる。

## 移行前の状況

移行元はWordPressのJINテーマで運営していたフットサル戦術ブログである。記事には次のような要素が含まれていた。

- カテゴリを含む階層型パーマリンク
- WordPressのメディアライブラリに保存した画像
- Gutenbergのブロックコメント
- JINテーマ固有のHTMLや装飾クラス
- URLを単独で貼ったYouTube・Xの埋め込み
- JINのブログカード
- 目次プラグインのショートコード
- codocによる有料記事
- RSS、サイトマップ、構造化データ

WordPressから記事本文をコピーするだけなら難しくない。しかし、その方法では記事数が増えるほど表記揺れやリンク切れが発生し、再実行もできない。そこで、WordPress標準のWXRエクスポートを入力にして、Markdownへ一括変換する方針を採用した。

## 最初に決めたこと：WordPressを再現しすぎない

移行先では、WordPressの内部構造をそのままNext.jsへ持ち込まなかった。

WordPressでは投稿、固定ページ、カテゴリ、添付ファイルなどがデータベースに保存され、テーマとプラグインが表示を組み立てる。移行後は、記事をMarkdown、メタデータをfrontmatter、画像を静的ファイルとしてGitで管理する構成にした。

```text
content/
  posts/**/*.md
  pages/*.md
  categories.json

public/
  images/posts/**

scripts/migrate/
  parse-wxr.ts
  build-category-map.ts
  html-to-markdown.ts
  wxr-to-markdown.ts
```

役割は明確である。

- `parse-wxr.ts`でWXRを解析する
- `build-category-map.ts`で親子カテゴリを復元する
- `html-to-markdown.ts`でWordPress由来のHTMLをMarkdownへ変換する
- `wxr-to-markdown.ts`で記事・固定ページ・画像を所定の場所へ出力する

この分割によって、パーサ、HTML変換、ファイル配置を個別に修正できるようになった。移行処理は本番のリクエスト時には動かさず、必要なときだけ実行するバッチとして扱っている。

## WXRをMarkdownへ変換する

### 1. まずWXRを正常に読める状態にする

実データのWXRには、XMLパーサが受け付けない制御文字が混ざることがあった。そこで、エクスポートファイルから不正な制御文字を除去し、クリーンなWXRを作成してから変換するようにした。

```bash
node -e "require('fs').writeFileSync(
  'wp-mirror/export_clean.xml',
  require('fs')
    .readFileSync('wp-mirror/export.xml', 'utf-8')
    .replace(/[\x00-\x08\x0b\x0c\x0e-\x1f\x7f]/g, '')
)"
```

元データを直接書き換えず、入力ファイルと変換用ファイルを分けたのも重要だった。変換に失敗しても元のWXRへ戻れるためである。

### 2. URLをfrontmatterとして保持する

各記事は、本文と次のようなfrontmatterへ変換した。

```yaml
---
title: "記事タイトル"
slug: fixo
wpId: 7457
category: base
categoryPath:
  - base
date: "2025-03-29"
updated: "2025-03-29"
draft: false
excerpt: "記事の要約"
cover: /images/posts/2025/03/cover.jpg
tags: []
---
```

特に残してよかったのが`wpId`と`categoryPath`である。

`wpId`は公開画面には不要だが、WordPress側の記事と移行後のMarkdownを照合するときに使える。`categoryPath`は、単一カテゴリ名ではなく親から子までのパスを持つ。これにより、`/set-play/opposition-half-ki/chon-don/`のような既存の階層型URLを機械的に復元できた。

現在はさらに、URLやファイル名を変更しても購入情報などとの関連が切れないよう、`articleId`という不変IDも追加している。移行直後には見えていなかったが、コンテンツを外部システムと結び付けるなら、URLやWordPress IDとは別の永続的なIDを最初から持たせる方が安全である。

### 3. HTMLを一度正規化してからMarkdown化する

WXRの本文は、きれいなHTMLとは限らない。Gutenbergのコメント、テーマ固有のラッパー、空段落、目次ショートコードなどが混在している。

そこで、CheerioでDOMとして読み込み、不要な要素を整理してからTurndownへ渡した。

主な変換は次の通りである。

- WordPressのブロックコメントを削除
- `[toc]`など目次プラグインの記法を削除
- 空段落を削除
- JINの2カラム用ラッパーを外し、中身だけ残す
- WordPress内の絶対URLをサイト内相対URLへ変換
- `figure`と`figcaption`をMarkdown画像とキャプションへ変換
- `srcset`や`loading`など、移行後に不要な画像属性を除去

ここで意識したのは、テーマのHTMLを完全再現するのではなく、記事の意味を残すことだった。たとえば2カラムの見た目が消えても、左右に入っていた文章や画像は失わない。テーマ固有のDOMを新しいサイトへ持ち込むより、Markdownとして長く保守できる形を優先した。

## 画像はURLだけでなくファイル本体も移す

WXRだけでは、画像ファイル本体は移行できない。そのため、WordPressの`wp-content/uploads`を別途取得し、`public/images/posts/{year}/{month}/`へコピーした。

変換スクリプトでは添付ファイルURLの対応表を作り、本文中の次のようなURLをローカルパスへ置換する。

```text
https://futsal.tech/wp-content/uploads/2021/08/example.jpeg
↓
/images/posts/2021/08/example.jpeg
```

サムネイル用の`-300x200`のようなサイズ接尾辞やクエリ文字列も正規化した。本文が縮小版URLを参照していても、可能な限り元画像へ対応できるようにするためである。

移行が一段落した後に、リポジトリ内の画像をWebPへ変換する処理を追加した。その後、表示サイズに応じたレスポンシブ画像も生成するよう改善している。これは「移行」と「最適化」を分けた例である。最初からすべてを完成させようとせず、まず欠損なく移し、その後に配信サイズを改善した。

## URLを変えないことを最優先にした

既存サイトには検索流入があるため、URL変更は影響が大きい。移行スクリプトでは、WordPressのURLと、`categoryPath`と`slug`から生成したURLを比較し、不一致を一覧化するようにした。

```ts
const expectedUrl = `${SITE_URL}/${categoryPath.join("/")}/${post.slug}/`;
const normalizedLink = post.link.replace(/\/$/, "") + "/";
const normalizedExpected = expectedUrl.replace(/\/$/, "") + "/";

if (normalizedLink !== normalizedExpected) {
  urlMismatches.push(
    `slug=${post.slug} | WP link: ${post.link} | Generated: ${expectedUrl}`,
  );
}
```

URLを維持できないページには、Next.jsの`redirects()`で301リダイレクトを設定した。対象は、たとえば次のようなURLである。

- `/feed/`から`/feed.xml`への移行
- `/wp-sitemap.xml`から`/sitemap.xml`への移行
- 旧固定ページを記事として再分類した際のURL変更
- 過去に手作業で作成した別名URL

重要なのは、「主なページだけ目視する」のではなく、変換時に全件比較することだった。70記事を人間が確認すると見落としが出る。移行スクリプトに検証を含めれば、変換ロジックを直すたびに同じ基準で再確認できる。

## Next.jsでは1つの動的ルートから静的生成する

移行先はNext.js 16のApp RouterとReact 19で構築した。記事、カテゴリ、固定ページはcatch-allルートで解決し、`generateStaticParams`と`dynamic = "force-static"`を使って静的生成している。

```ts
export const dynamic = "force-static";

export async function generateStaticParams() {
  return getAllStaticPaths();
}
```

Markdownは`gray-matter`でfrontmatterと本文に分け、remark・rehypeのパイプラインでHTMLへ変換する。記事ページだけでなく、カテゴリ一覧、パンくず、目次、RSS、サイトマップ、JSON-LDも同じコンテンツモデルから生成する構成にした。

この方式では、公開ページの生成時にWordPressや外部データベースへ問い合わせる必要がない。記事更新はMarkdownを変更してビルドするだけで、コンテンツの差分もGitで追跡できる。

## WordPressの「便利だった挙動」を選んで戻す

Markdownへ変換すると、WordPressが自動で行っていた表示機能は失われる。そこで移行直後に、YouTube・Xの埋め込みと内部リンクカードを順に実装した。

ルールは、執筆者が覚えやすい形にした。

- YouTubeのURLを単独行に置くとレスポンシブな動画へ変換する
- Xの投稿URLを単独行に置くと埋め込みへ変換する
- サイト内URLを単独行に置くとタイトル、抜粋、画像を含むカードへ変換する

WordPressのHTMLをそのまま保存するのではなく、Markdown上はURLだけを残し、表示時に変換する。これにより、本文は読みやすいまま、WordPress時代の編集体験もある程度維持できた。

目次も同様で、記事にショートコードを残すのではなく、見出しから自動生成する。スマートフォンではアコーディオン、PCでは追従表示に分けた。WordPressのプラグインを置き換えるときは、プラグイン名ではなく「読者と執筆者にとって必要だった機能」を特定すると設計しやすい。

## 移行後に追加した運用の仕組み

初期移行のあと、次のような順序で機能を追加していった。

1. WXR変換、Markdown管理、静的ページ生成、YouTube・X埋め込み、内部リンクカード、CI
2. codocのメタデータとペイウォール位置の移行
3. 画像サイズの取得、記事表示コンポーネント、SEOの改善
4. 画像のWebP化、YouTubeリンク切れチェック
5. Xリンク切れチェック、Search Console向けメタデータ
6. 多言語化と翻訳記事の追加
7. レスポンシブWebP画像
8. Cloudflare WorkersとOpenNextによる配信へ移行
9. 課金基盤や検索など、サイト運営機能を拡張

初期のREADMEではVercelへのデプロイを想定していたが、後にCloudflare WorkersとOpenNextへ配信基盤を変更している。コンテンツをMarkdownと静的アセットに分離していたため、ホスティング先の変更が記事データの再移行に波及しなかった。

また、リンク切れチェックをCIへ追加したことも効果が大きかった。移行時に正しく表示できても、外部動画やSNS投稿は後から削除される。移行完了を一度きりのイベントではなく、継続的な検証へつなげる必要がある。

## 苦労した点と、やり直すなら変えること

### コンテンツの分類は「投稿か固定ページか」だけでは決まらない

WordPress上では固定ページでも、実態は長文の戦術記事というページがあった。これらは移行時に`content/posts/base/`へ振り分け、旧URLから301リダイレクトした。

CMSの投稿タイプをそのまま移植するのではなく、移行後にどう一覧表示し、検索し、関連記事として扱うかで分類を決めるべきだった。

### テーマ固有表現は例外が増えやすい

JINの装飾、Gutenbergコメント、ショートコード、ブログカード、有料記事ブロックは、それぞれ別の変換規則が必要だった。HTMLを正規表現だけで処理すると壊れやすいため、DOMとして解析できるものはCheerioで扱い、最後の整形だけを限定的な正規表現にした。

移行前に、記事内で使われているブロックやショートコードの種類を集計しておけば、変換後の手戻りをさらに減らせたと思う。

### 不変IDは最初に設計する

移行当初はWordPress IDとURLがあれば十分だった。しかし有料記事の購入情報を扱うようになると、slugやファイルパスを変更しても変わらない識別子が必要になった。そのため、後からUUIDベースの`articleId`を導入した。

分析、課金、翻訳などへ発展する可能性があるなら、CMS由来のIDとは別に移行先の不変IDを最初から用意する方がよい。

### 変換結果の品質チェックもコードにする

ビルドが通っても、記事品質が正しいとは限らない。このリポジトリでは、Markdown記法、YouTubeリンク、Xリンク、ペイウォール位置などを検査するスクリプトを後から追加した。

移行前に最低限、次の検査を自動化しておくと安全である。

- WordPressと移行後の公開記事数が一致するか
- URLの一致、または301リダイレクトがあるか
- 参照画像がすべて存在するか
- 内部リンクの遷移先が存在するか
- title、description、canonical、構造化データが出力されるか
- 有料記事の公開範囲が移行前と一致するか

## 実際に使った移行手順

最終的な流れは次のようになった。

1. WordPress管理画面から全コンテンツをWXRでエクスポートする
2. `wp-content/uploads`を取得する
3. WXRから不正な制御文字を除去する
4. 変換スクリプトを`--dry-run`で実行し、件数とURL差分を確認する
5. Markdown、カテゴリJSON、画像を出力する
6. Next.jsをビルドし、全ページが静的生成されることを確認する
7. 旧URL、RSS、サイトマップ、内部リンク、画像を確認する
8. 変更できないURLは維持し、変更が必要なURLには301リダイレクトを設定する
9. 本番切り替え後も、Search Consoleとリンクチェックで継続監視する

変換コマンドにはdry-runを用意した。

```bash
npx tsx scripts/migrate/wxr-to-markdown.ts --dry-run
npx tsx scripts/migrate/wxr-to-markdown.ts
npm run build
```

何度でも同じ入力から再生成できることが、手作業移行との最大の違いだった。

## まとめ

WordPressからNext.jsへの移行は、CMSをフレームワークへ置き換える作業ではない。WordPressがまとめて提供していた責務を、コンテンツ、ルーティング、表示、SEO、画像、収益化、運用監視へ分解する作業である。

今回の移行で特に有効だったのは、次の4点だった。

1. WXRからMarkdownへの変換をスクリプト化し、再実行可能にする
2. `categoryPath`から旧URLを再現し、全件を機械的に比較する
3. テーマ固有HTMLは見た目ではなく意味を残す形へ正規化する
4. 移行後の改善を前提に、コンテンツと配信基盤を分離する

最初のコミットで記事と画像をまとめて移行し、その後のコミットで埋め込み、SEO、画像最適化、多言語化、課金、配信基盤を段階的に改善した。この順序だったからこそ、70記事を抱えた状態でも移行作業を制御できた。

WordPressサイトの移行では、完成形を一度に作るよりも、まずURLとコンテンツを失わずに移すことが重要である。そのうえで、テーマやプラグインが提供していた機能を一つずつ選び直す。結果として、それが最も安全で、移行後も育てやすい構成になった。
